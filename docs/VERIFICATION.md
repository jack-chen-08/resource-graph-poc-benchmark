# 测试方法：怎么验证这份报告里的每个说法

报告里的数字都可以用下面四条命令复核，不需要读代码。所有命令都在 `docker compose` 里跑，
不依赖宿主机装 Postgres 或 Python 库。

```bash
# 1) 从零跑一遍，生成报告（约 6 分钟，含 72,000 条向量的规模外推）
docker compose up --build

# 2) 自检：数据规模、两方案结果等价、目标阈值（约 10 秒，数据已就绪时）
docker compose run --rm poc python -m src.selftest

# 3) 看报告
cat docs/BENCHMARK.md

# 4) 看机器可读结果，自己算任意统计量
cat reports/benchmark.json
```

## 自检到底查了什么

`src/selftest.py` 不是"跑完打印 OK"的摆设，它按三类断言逐条核对，任一条不过就以非 0 退出：

| 类别 | 断言 | 为什么必须有这一条 |
| --- | --- | --- |
| 数据规模 | `node` = 20,000 行（企业 6,000 / 联系人 8,000 / 能力 2,000 / 需求 1,000 / 标签 3,000）、`edge` = 100,000 行 | 造数时若随机采样写错（比如需求到能力没配齐），规模会静默缩水，压测结论就失去可比性。第一版就踩过：实际只生成 99,945 条，断言直接把它拦下 |
| 语义等价 | 四类查询各取 20 组参数，方案 A 与方案 B 的结果集**逐条相等** | 两个方案的 SQL 不同（递归 CTE vs 闭包表 / 路径表），只要有一处关系方向或去重逻辑写错，两边条数就会不同；没有这条断言，"B 更快"可能只是"B 少查了东西" |
| 目标阈值 | Q1 P95 < 300 ms、Q4 P95 < 1000 ms，两方案都要过 | 直接从 `reports/benchmark.json` 读，避免报告文字与实测数据脱节 |

## 结果一致性怎么验

Q1～Q4 每组 200 组参数，**同一批参数**分别喂给两个方案；除耗时外还记录返回条数
（报告第 2 节"结果条数"列）。两方案在同参数下条数一致，才说明"快"不是靠少返回换来的。
自检里进一步收紧：不只比条数，比 id 集合是否相等。

## 执行计划证据

报告第 6 节列出每类查询在两个方案下**实际走的访问路径**（`EXPLAIN (ANALYZE, FORMAT JSON)`
抓取后提取节点类型与索引名）。这一节专门防"我以为走了索引"：

- 方案 A 的 Q1/Q4 是递归 CTE 逐跳展开，每跳走一次边表索引；
- 方案 B 的 Q1/Q4 是一次闭包表 / 路径表查找；
- Q3 两方案 SQL 完全相同，**实测在 8,000 条向量这一档优化器没有选 HNSW**（两方案都走精确扫描）。
  这不是代码写错，而是规模不够——交叉点见第 8 节的外推实验。

## 为什么单独做规模外推

20,000 节点里只有 8,000 条向量，精确扫描约 20 ms，任何优化器都会判断"索引不划算"。
只交这一组数据，结论会退化成"向量索引没用"，那是错的。所以把同一批真实向量复制到
8,000 / 24,000 / 72,000 三档，单独测"纯向量 top-100 检索"，量出加速比与召回随规模的变化。

这一节是**诊断实验**，不是目标查询的成绩单：其中耗时用 `SET enable_seqscan = off` 强制走索引，
目的是量索引本身的代价，报告已注明。

## 已知的不严谨处（不藏）

- 单机、单连接、串行压测，**没有并发**。锁竞争、连接池、缓存命中变化均未覆盖。
- 向量是随机生成的，近邻区分度低，ANN 召回（52%～78%）是**下限**情形，不能当"生产可用"结论；
  真实 embedding 上线前必须重测第 7 节。
- 机器性能影响绝对值：换机器后 P50/P95 会变，但方案之间的倍数关系稳定。
  对照时必须在同一台机器上重跑两个方案。
- 数据是虚构的，度分布与社区结构不具真实图谱特征，因此"多跳展开代价"在真实数据上只会更差、不会更好。
